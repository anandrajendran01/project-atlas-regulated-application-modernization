# Project Atlas — Case Study Assumptions
## Purpose
This document establishes the baseline assumptions used throughout the Project Atlas portfolio case study.

All financial values, resource information, schedules, operational metrics, benefits, risks, and organizational details are synthetic and have been created solely for project-management demonstration purposes.

Maintaining a common assumption set ensures consistency between the project's scope, schedule, budget, resource plan, risk register, status reports, earned-value calculations, and closure documentation.

## Project Environment
**Project:** Project Atlas  
**Business Context:** Regulated Enterprise Environment  
**Project Type:** Enterprise Application Modernization  
**Delivery Approach:** Predictive / Waterfall  
**Planned Duration:** 9 Months  
**Production Hypercare:** 4 Weeks

The project replaces a legacy enterprise application with a modern web-based platform and includes application development, systems integration, data migration, validation, deployment, and transition to operations.

## Delivery Scope
The project includes:

- Modernization of the existing enterprise application.
- Development and configuration of the replacement platform.
- Integration with four enterprise systems.
- Migration of required operational and historical data.
- System, integration, regression, validation, and user acceptance testing.
- Security and production-readiness assessments.
- End-user readiness and training.
- Production deployment.
- Four weeks of structured hypercare.
- Transition to business-as-usual support.

Major redesigns of connected enterprise systems, mobile application development, and broader analytics-platform transformation are outside the project scope.

## Project Organization
The core delivery organization consists of approximately 14 project resources excluding the executive sponsor.

Representative roles include:
- Project Manager

- Solution Architect
- Application Developers
- Integration Specialists
- Quality Assurance / Validation Analysts
- DevOps / Release Engineer
- Change and Training Support

Specialist vendor resources may be engaged where required for independent validation, security assessment, or specialist technical services.

## Workstreams

### Workstream 1 — Application Development

Responsible for solution design, application configuration and development, technical documentation, defect remediation, and implementation support.

### Workstream 2 — Integration & Data Migration

Responsible for enterprise integrations, data mapping, migration design, reconciliation, interface testing, and migration execution.

### Workstream 3 — Validation & Deployment

Responsible for quality planning, validation, testing coordination, UAT readiness, deployment governance, production readiness, hypercare, and transition.

## Financial Assumptions
### Cost Baseline / Budget at Completion

**₹2.40 Crore**

The cost baseline includes planned project expenditure and contingency reserve for identified project uncertainty.

### Management Reserve

**₹15 Lakh**

Management reserve is maintained outside the project cost baseline for unforeseen work within overall project scope and is not included in the project's Budget at Completion for earned-value measurement.

### Total Authorized Project Budget

**₹2.55 Crore**

Total Authorized Project Budget = Cost Baseline + Management Reserve

₹2.40 Crore + ₹0.15 Crore = ₹2.55 Crore

## Governance Assumptions

The project uses the following governance model:

**Weekly Project Delivery Review**  
Progress, milestones, blockers, dependencies, actions, and short-term priorities.

**Fortnightly Risk & Change Review**  
Review of significant risks, issues, proposed changes, dependencies, and required escalations.

**Monthly Steering Committee**  
Executive review of schedule, budget, scope, quality, major risks, decisions, and overall project health.

**Stage-Gate Reviews**  
Formal approval at defined points before progression to subsequent lifecycle stages.

## Quality Assumptions

The project operates within a regulated environment and therefore requires:
- Approved requirements before build completion.
- Requirements-to-test traceability.
- Documented system and integration testing.
- Formal user acceptance.
- Validation evidence.
- Production-readiness assessment.
- Controlled deployment approval.

No unresolved Severity-1 defects may remain at production release.

## Benefits Assumptions

The business case assumes that modernization will contribute to:
- Reduced legacy application support and maintenance expenditure.
- Reduced manual processing.
- Improved process efficiency.
- Improved integration reliability.
- Reduced production incidents.
- Improved audit and validation traceability.

Financial and non-financial benefits will be defined in greater detail within the Business Case and Benefits Management artifacts.

## Change-Control Principle

Once scope, schedule, and cost baselines are formally established, material changes will be assessed through integrated change control.

Approved changes affecting project baselines will be documented and reflected consistently across all impacted project artifacts.

This mechanism will also be demonstrated within the GitHub repository through controlled artifact updates and, where appropriate, branch and pull-request workflows.
